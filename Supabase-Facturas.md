# Cambios en Supabase — Tabla `facturas`

Este documento contiene **únicamente** los cambios a ejecutar manualmente en el proyecto
Supabase real — nada de código de la app. Sigue la misma convención que
`Supabase-SobresPresupuestarios.md`: primero se implementa y valida todo en modo
Demo/Local, y este SQL se ejecuta al final, paso a paso y confirmando cada uno antes de
pasar al siguiente.

## 1. Crear la tabla `facturas`

```sql
CREATE TABLE facturas (
    id bigint generated by default as identity primary key,
    "categoriaId" integer NOT NULL,
    "subcategoriaId" integer,
    concepto text NOT NULL,
    importe_total numeric NOT NULL,
    fecha_creacion date NOT NULL,
    fecha_cobro date,
    fecha_consumo_inicio date NOT NULL,
    fecha_consumo_fin date NOT NULL,
    reparto jsonb NOT NULL DEFAULT '[]'::jsonb
);
```

- `fecha_cobro` nulo = factura pendiente de pago (todavía no tiene movimientos).
- `reparto` guarda el importe por mes: `[{ "mes": "2026-01", "importe": 12.34 }, ...]`.
- No lleva claves foráneas, igual que `movimientos."categoriaId"`/`"subcategoriaId"` (enteros
  sueltos sin FK).
- Después de crear la tabla, **replica en `facturas` las mismas políticas RLS/policies que
  ya tengas en `movimientos`**, para que la anon key pueda leer y escribir (la app no
  puede hacer esto por ti: revisa Authentication → Policies en el proyecto Supabase).

`movimientos."facturaId"` (columna `text` que ya existe desde
`Supabase-SobresPresupuestarios.md`) no cambia de tipo: a partir de ahora guardará
`id::text` de una fila de `facturas` en vez del UUID que generaba antes la app.

## 2. Backfill del histórico ya agrupado por `facturaId` (UUID)

Reconstruye una fila de `facturas` por cada `facturaId` distinto que ya exista en
`movimientos` (facturas divididas en varios meses dadas de alta antes de este cambio), y
re-apunta esos movimientos al nuevo id entero. Usa una columna temporal
`legacy_factura_uuid` para poder cruzar el id nuevo con el UUID antiguo, y se borra al
terminar.

```sql
ALTER TABLE facturas ADD COLUMN legacy_factura_uuid text;

WITH grupos AS (
  SELECT
    "facturaId" AS old_id,
    (array_agg("categoriaId" ORDER BY fecha_referencia))[1] AS "categoriaId",
    (array_agg("subcategoriaId" ORDER BY fecha_referencia))[1] AS "subcategoriaId",
    regexp_replace((array_agg(concepto ORDER BY fecha_referencia))[1],
                    '\s*\(\d+/\d+\)\s*$', '') AS concepto,
    SUM(importe) AS importe_total,
    MIN(fecha) AS fecha_creacion,
    MIN(fecha) AS fecha_cobro,
    MIN(fecha_referencia) AS fecha_consumo_inicio,
    MAX(fecha_referencia) AS fecha_consumo_fin,
    jsonb_agg(jsonb_build_object('mes', to_char(fecha_referencia, 'YYYY-MM'),
                                  'importe', importe) ORDER BY fecha_referencia) AS reparto
  FROM movimientos
  WHERE tipo = 'GASTO' AND "facturaId" IS NOT NULL
  GROUP BY "facturaId"
)
INSERT INTO facturas ("categoriaId", "subcategoriaId", concepto, importe_total,
                       fecha_creacion, fecha_cobro, fecha_consumo_inicio,
                       fecha_consumo_fin, reparto, legacy_factura_uuid)
SELECT "categoriaId", "subcategoriaId", concepto, importe_total, fecha_creacion,
       fecha_cobro, fecha_consumo_inicio, fecha_consumo_fin, reparto, old_id
FROM grupos;

UPDATE movimientos m
SET "facturaId" = f.id::text
FROM facturas f
WHERE f.legacy_factura_uuid = m."facturaId";

ALTER TABLE facturas DROP COLUMN legacy_factura_uuid;
```

Notas:
- `fecha_cobro` se rellena con la misma `fecha` que ya tenían esos movimientos (ya
  estaban cobrados/pagados; es lo que ejecutó la migración anterior a mano).
- Los movimientos sueltos de estas categorías que nunca tuvieron `facturaId` (facturas de
  un solo mes dadas de alta con el formulario normal, antes de este cambio) **no se
  tocan**: se quedan como movimientos sueltos, sin fila en `facturas`.
- Revisa el resultado (`SELECT * FROM facturas`) antes de dar el paso por bueno, y
  confirma con la app (pestaña Facturas → 🧾 Por factura) que las facturas antiguas
  aparecen con su fecha de creación, fecha de cobro e importe correctos.
